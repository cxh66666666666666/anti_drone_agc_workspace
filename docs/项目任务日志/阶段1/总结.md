## 二、当前架构基线（决策 1/3/4 的依据）

M0 契约 §一冻结的分工是：

> 空中平台提供**目标与环境信息**；地面车据此**规划**、运动、避障并反馈。

对应实现链路（今天样例实测）：

```text
gt_adapter / air_fusion ──▶ /agc/targets ──▶ task_manager（算 /agc/ground/goal）
                                                   │
                                                   ▼
                              ground_planner（A* → /agc/ground/path）
                                                   │
                                                   ▼
                              ground_commander（/agc/ground/cmd_vel）
                                                   │
                                                   ▼
                              ground_drive_adapter（set_model_state 写 agc_car）
```

状态机：`IDLE → AIR_SEARCH → TARGET_ACQUIRED → GROUND_APPROACH → TRACKING_SUCCESS`（阶段 A 终态）。

- **决策 1**：感知仍为「真值/加噪坐标」的坐标发送，不接真实相机/雷达。
- **决策 3**：规划权在地面侧（`ground_planner`），无人机只做感知源，不改。
- **决策 4**：不做拦截机构，因此阶段 A 的 `TRACKING_SUCCESS`（含义「抵近并持续跟踪」）即为最终成功，且**不得表述为拦截完成**；`INTERCEPT_CONFIRMED` 保持禁用。

## 三、决策 2 的说明（无人机追踪）

### 3.1 现状为什么不「丢目标」
当前 `air_perception` 是由 Gazebo 真值派生的感知仿真，**没有视场角（FOV）/距离门控**，只有噪声、延迟、丢包三项（见 `perception_sensors.yaml`）。所以无人机定在原地不动，目标飞多远都「看得见」；只有在注入丢包时才会 `TARGET_LOST`。

因此**决策 2 是物理合理性问题，不是当前缺陷**：真实系统里无人机必须保持对移动目标的观察，否则会因视野丢失目标。

### 3.2 问题形态（本轮结论）
- 目标是**会移动的无人机**，无人机需要**位置跟随**；
- 跟随要求**保持在一定距离范围内**（有下限，**不能太近**）——即"带死区的保持距离"，而非贴合/伴飞。

### 3.3 实施要点（登记，尚未做）
- 契约约束：**空中 setpoint 的唯一发布者仍是 `lqr_tracker_node`**（M0 §四），跟随逻辑必须落在该控制链内，不能新增并行 setpoint 发布者。
- 参考点算法（建议）：设无人机水平位置 `d`、目标水平位置 `t`，`dist = |d - t|`，距离带 `[min_m, max_m]`：
  - `desired = clamp(dist, min_m, max_m)`；
  - 参考点 `ref = t + desired · unit(d - t)`（保持当前方位，仅调整距离）；
  - `dist` 落在带内时 `ref ≈ 当前位置` → 无人机保持不动，实现「范围内不机动」。
- 距离与高度作为参数（如 `follow/min_m`、`follow/max_m`、跟随高度取目标同高 `2.0 m`）。
- **影响**：改变无人机飞行行为，会使既有以「定点悬停（`step`）」为前提的证据（M1/M2/M6 移动目标场景）需要**重新验收**；建议作为 M0 契约的**能力新增**（不新增话题则可不变更契约版本，但需在验收文档中说明口径）。
