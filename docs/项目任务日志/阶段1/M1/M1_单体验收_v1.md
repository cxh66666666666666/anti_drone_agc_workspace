# M1 单体验收 v1：稳定单体启动、复位、退出

> 2026-09-27；依据 [下一阶段任务清单.md](../../项目指导书/下一阶段任务清单.md) 的 M1（P0）与 [M0_接口契约_v1.1.md](../M0/M0_接口契约_v1.1.md) 第六、七节。证据根目录：`experiments/agc_runs/`。本版结论只覆盖「单体启动/复位/退出」，不含 M2–M9，也不宣称拦截完成。

## 一、任务口径

M1 要求核查：无人机起飞门禁、EKF/位姿异常、地面车控制权交接、旧进程残留、每次失败原因。验收交付物三项：固定简单场景的连续运行记录；每次有启动状态、复位结果、进程/发布者清单和失败原因；退出后无本次遗留进程。

非目标（按用户决定）：不改动无人机侧 OFFBOARD/LQR 控制时序；AUTO.LAND 抖动只作为启动异常项记录；不推进 M2–M9。

本轮范围：**记录与分类 + 编排层修复**。编排层修复为两项：

1. 把 `handover_ok` 设为 start 硬前置，未通过不进入 attempt 并落盘证据（第六节第 1 项）。
2. 修掉 start 门禁**自调用复位**造成的 odom 自伤竞态：门禁改为「先场景复位、后复核 odom」并加有界等待（第五、六节）。此项由用户决定在 M1 内追加修复，仍只动 `task_manager` 的门禁顺序与等待，不动无人机侧时序。

为满足交付物所需的 run 日志/编排记录补齐一并列在第六节。

## 五、启动异常项

### 5.1 起飞期间 OFFBOARD → AUTO.LAND → OFFBOARD 抖动（记录，未修）

- 权威批次 3 次起飞**均**出现该模式序列（`… → OFFBOARD → AUTO.LAND → OFFBOARD`）；上一批（`_m1_batch_20260927T042505`）为 2/3。
- 记录值：`max_setpoint_gap_s` = 1.228 / 1.251 / 1.287 s，均大于 `air/setpoint_gap_max_s`（0.2 s）。
- 判定：该间隔落在**起飞窗口**，不是交接窗口。交接本身无空窗（`handover_gap_s` 0.0572/0.0237/0.0467 s < 0.2 s），`handoverOk()` 只看交接间隔，故门禁仍通过。按用户决定不改无人机侧时序，仅作为启动异常项记录。

### 5.2 start 后同拍 `ODOM_INVALID`：门禁自调用复位造成的自伤竞态（已修）

**机制**（修复前）：`/agc/task/start` 的门禁第 7 项**自身**调用 `/agc/scenario/reset`，该复位会调用 `/agc/air/recalibrate`（[scenario_reset.cpp](../../../src/air_ground_core/src/scenario_reset.cpp#L127-L139)），而重标定**无条件**将 `/agc/air/odom_valid` 置 false 并等下一帧 MAVROS 才恢复（[air_odom_adapter.cpp](../../../src/air_ground_core/src/air_odom_adapter.cpp#L356-L367)）。修复前门禁第 3 项的 odom 检查发生在这场复位**之前**，于是「刚通过门禁」与「odom 已被自己打无效」在同一拍并存，`evaluate()` 立即结算 `INFRA_FAILURE/ODOM_INVALID`。

**修复前证据**（`_m1_batch_20260927T035426`，2/30）：run `20260927T040627_a8613e` 的 `reset_log.jsonl`（epoch 11）与 `state_events.jsonl` 中 start、`INFRA_FAILURE` 三者同为 `t_sim=248.612`；`air_calibration.json` 的 `t_calib_sim=248.54`（失败前 0.07 s 发生重标定）；同目录两条 odom 流未中断（air 约 30 Hz、末尾年龄 0.07 s；ground 0.008 s）→ 排除「消息过期」。

**修复**（本版）：门禁改为**先复位、后复核 odom**，并在复核失败时做有界等待：

- 顺序：场景复位 → odom 复核（[task_manager.cpp](../../../src/air_ground_core/src/task_manager.cpp#L387-L413)）。
- 等待：`waitOdomRestored()`（[task_manager.cpp](../../../src/air_ground_core/src/task_manager.cpp#L352-L364)）在上限 `/agc/start/odom_recheck_timeout_s`（3.0 s，[agc_params.yaml](../../../src/air_ground_core/config/agc_params.yaml#L116-L119)）内以 50 ms 步长 `spinOnce` 续收 odom 后复核；超时仍不通过则按门禁失败处理（诚实失败，不再产生自伤 run）。
- 证据：门禁明细新增 `odom_wait_s` 与 `odom_probe`（复位前/后的 valid 与年龄）。

**修复后证据**（`_m1_batch_20260927T051409`）：30/30 门禁通过、0 次 `INFRA_FAILURE`；4/30 次复核出现 0.052–0.056 s 的等待（3.3）。注意上一批 `_m1_batch_20260927T042505` 的 0/30 **不能**作为竞态已消除的证据——该竞态与重标定完成时刻相关，属概率事件；本批的 4 次等待即为该窗口存在的直接记录。

### 5.3 终态后自动新开的 run 目录

`/agc/task/state` 进入终态时 logger 立即结算并新开 run 目录，因此每段会话收尾会留下一个「无 attempt」的空目录（`startup`/`nodes` 等写 `null`，`finalize_reason=shutdown`）。`summarize_runs.py` 已按 `no_attempt_runs` 排除，不计入分母。此为 M0 既有设计，本轮不改。

## 八、未决事项

1. 「终态→同码终态」连续两次门禁失败时，run 日志仍会按广播去重（该 attempt 的失败只在 `batch.json` 与 `state_events.jsonl` 留痕）；如需逐 attempt 一一对应，需在 M2 一并设计 run 边界。
2. 起飞窗口 AUTO.LAND 抖动的来源未定论（是否为 `drone_launch_controller` 的 OFFBOARD 维持超时或 PX4 侧保护），本版只记录现象与量值。
3. 复位后 odom 短暂未通过（4/30）未逐案区分是空中重标定清空 `air_valid` 还是地面 odom 瞬态；现有 `odom_probe` 只记复位前/后两拍，若 M2 需要精确定位，可再补首次复核失败的即时快照。
4. `air_handover.json` 是滚动快照，写在写入当时的 run 目录，因此每循环前几个 attempt 的副本里 `hold_triggered=false`（快照时点早于终态），完整悬停验证结果只在同一循环末 attempt 的副本中（`hold_ok=true`、最大偏差约 0.0002 m）。读该文件时须以同一 run 会话最后一次写入为准。

> 以上第 1–4 项已于 2026-09-27 全部修复，见第九节。
