# M1 计划：稳定单体启动、复位、退出

## Context（为什么做）

《下一阶段任务清单》M1（P0）要求交付：**固定简单场景连续运行记录；每次有启动状态、复位结果、进程/发布者清单和失败原因；退出后无本次遗留进程**。

M0 已把接口层与第一条端到端闭环落地，`agc_run_logger` 已按契约 §六写 run 日志，但与 M1 交付口径相比存在硬缺口：

- 现有 `summary.json` 的 `startup_result` 实际读的是 `/agc/reset/last_result`（**复位结果**，不是启动状态），启动状态无结构化记录；
- **进程/发布者清单无任何落盘**（仅 `air_control_bridge` 的 `air_handover.json` 记录了 setpoint 单话题发布者）；
- **退出后遗留进程核查无落盘**（`cleanup_and_exit` 只做 pkill，无核查产物）；
- **无连续运行编排**（`start_agc_collab.sh` 只能单次 launch + 单样例）。

已定位的启动不稳定根因（用现有 run 日志核实）：当前 6 次 infra 失败中 **5 次是启动门禁 `air_handover:false`**——`start` 在 LQR 尚未接管时被调用，属编排层时序竞态；另 1 次是 M0 故意注入的 ODOM_INVALID。另观察到起飞阶段 MAVROS 出现一次 `OFFBOARD→AUTO.LAND→OFFBOARD` 抖动（`air_handover.json` 的 `mavros_mode_changes`）。

预期结果：M1 结束时，固定简单场景可连续重复运行，每次尝试都有启动/复位/进程与发布者/失败原因的可核查记录，且整轮退出后无遗留进程；启动竞态在编排层被消除。

## 已确认的范围决策

- **批跑形式**：两种都做。先「单次启动内连续 10 次 attempt」，再做「启动→退出」全循环 3 次。
- **根因处理**：先记录与分类；M1 内**只做编排层修复**（把「等待 handover_ok」设为 start 的硬前置并落盘证据）。**不改动无人机侧控制时序**，AUTO.LAND 抖动只作为启动异常项记录。

## 变更清单

### 1. `src/air_ground_core/src/agc_run_logger.cpp`（核心加装）
在 `RunRecorder::finalize()` 的 `summary.json` 中补齐每 run 证据（复用 `agc::JsonObj` / `writeJsonAtomic`）：

- `startup`：`gate`（读新参数 `/agc/start/last_gate_json`）、`handover_ok`/`handover_gap_s`/`max_setpoint_gap_s`/`mavros_mode`（读 `/agc/air/handover_json`）、`air_calibration_residual_m`/`usable`（读 `/agc/air/calibration_json`）、`drive_backend`/`drive_backend_ok`、`air_odom_valid`/`ground_odom_valid`、`use_sim_time`、`single_world`、`contract_version`、`scenario_id`。
- `reset_result`：`last_result` + `epoch`（run 开始时），与 `startup_result` 解耦。
- `nodes`：ROS 节点名清单（`ros::master::getNodes`）。
- `publishers`：8 个契约话题的实际发布者节点（`getSystemState`，对齐 `task_manager.cpp:publishersOf` 的 XMLRPC 解析写法）。
- `processes`：关键 OS 进程清单（扫 `/proc/*/comm`|`cmdline`，按 px4/gzserver/mavros/各协同节点名过滤），用于证明唯一写入者与无重复进程。
- 新增 `single_world` 判定复用 `task_manager.cpp:runGate` 的 `lastSegment` + ground_gazebo 检查。
- 保留 `clean_exit` 语义不变；`summarize_runs.py` 不读 `startup_result`，改名不破坏聚合口径。

### 2. `src/air_ground_core/src/task_manager.cpp`（最小改动）
在 `handleStart()` 中把门禁结果写入新参数 `/agc/start/last_gate_json`（`gate.json()` + `passed` 布尔 + 时间戳），无论通过与否都写，供 run logger 读取门禁明细。

### 3. `scripts/start_agc_collab.sh`（编排层修复 + 连续运行 + 退出核查）
- 新增选项：`--repeat <N>`（默认 1，单次启动内 attempt 数）、`--cycles <M>`（默认 1，启动→退出全循环数）、`--scenario <file>`（默认 `config/scenario_flat.yaml`）。
- **编排层门禁修复**：把现有「等待 `/agc/air/handover_ok=true`」从告警升级为**硬前置**；未在超时内通过则标记 startup 异常并按分类记录，不再进入 attempt（消除 STARTUP_FAILURE 竞态）。
- **连续 attempt 循环**（N 次）：`reset` → 等 `SUCCESS` + 空地 odom 恢复 → `start` → 等终态 → 记录 `run_dir/final_state/reason_code`。固定简单场景不做注入。
- **全循环**（M 次）：完整 launch → 起飞 → 交接核查 → N 次 attempt → 记录退出前进程清单 → `cleanup_and_exit` → 退出后核查关键进程是否清空。
- 新增 `record_proc_list()` / `check_leftovers()` 函数（`pgrep`/`ps` 抓关键进程名，与 `cleanup_procs` 名单一致）。
- 批跑产物：`experiments/agc_runs/m1_batch_<ts>/batch.json`，含每 attempt 记录、每循环的起飞信息（connected/armed/mode/pose 到位/交接 gap）、退出前后进程清单与 `leftovers`。
- 在栈存活期间调用一次 `audit_interfaces.py`，把接口现场核查快照纳入批产物。

### 4. `docs/项目任务日志/M1/M1_单体验收_v1.md`（新增，唯一新增文档）
记录 M1 定义与边界、7 项检查项结论、加装的记录口径、连续批跑结果表、失败分类与根因、退出无残留证据、状态标识（未开始/进行中/已验收/阻塞）。历史措辞按清单「决策与定稿规则」处理，不设会签门槛。
